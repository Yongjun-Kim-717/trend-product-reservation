# 발표 시연 체크리스트

이 문서는 `database/demo-reset.sql`을 실행한 뒤의 DB 상태를 기준으로 한다.

## 1. 발표 전 준비

- MariaDB에 `trend_product_db`가 생성되어 있는지 확인한다.
- 최신 `database/schema.sql`이 현재 백엔드와 같은 구조인지 확인한다.
- 발표 직전에 `database/demo-reset.sql`을 실행해 시연 데이터를 초기화한다.
- 백엔드와 프론트엔드를 실행한다.
  - 백엔드: `npm run start:backend`
  - 프론트엔드: `npm run dev:frontend`
- Kakao Developers JavaScript SDK 도메인에 접속 주소가 등록되어 있는지 확인한다.

## 2. 시연 계정

| 역할 | 아이디 | 비밀번호 | 상태 | 용도 |
| --- | --- | --- | --- | --- |
| 관리자 | `admin1` | `admin1234` | ACTIVE | 판매자 승인, 매장 승인, 검색 로그/미매핑 관리 |
| 소비자 | `consumer1` | `consumer1234` | ACTIVE | 상품 검색, 가게 정보 확인, 예약/취소 |
| 승인된 판매자 | `seller_ready` | `seller1234` | ACTIVE / APPROVED | 상품 등록, 재고 관리, 예약 처리 |
| 승인 대기 판매자 | `seller_pending` | `seller1234` | ACTIVE / PENDING | 판매자 승인 시연 |
| 정지 소비자 | `consumer_suspended` | `consumer1234` | SUSPENDED | 사용자 관리 시연 |

## 3. 시연 초기 데이터

- 승인된 판매자 `박판매 디저트`
- 승인 대기 판매자 `최승인 팝업`
- 승인된 매장
  - `두쫀쿠마스터`
  - `버터떡마스터`
- 승인 대기 매장
  - `승인대기 디저트샵`
- 등록 상품
  - `두쫀쿠`
  - `버터떡`
  - `소금빵`
- 미매핑 검색어
  - `말차푸딩`
  - `크림붕어빵`
  - `인하대 후문 디저트 추천`

## 4. 권장 발표 흐름

### 4.1 로그인/역할 분리

- 로그인 화면에서 역할 선택 버튼 없이 아이디/비밀번호만 입력한다.
- `admin1`로 로그인하면 관리자 화면으로 이동하는 것을 보여준다.
- 로그아웃 후 `consumer1`, `seller_ready`도 각 역할 화면으로 이동하는 것을 간단히 설명한다.

### 4.2 관리자: 판매자 승인

- `admin1`로 로그인한다.
- 관리자 화면에서 `판매자 승인` 탭을 연다.
- `최승인 팝업` 판매자가 `PENDING` 상태인 것을 보여준다.
- 승인 버튼을 눌러 `APPROVED`로 변경한다.
- 승인 전에는 판매자 기능 접근이 막히고, 승인 후에는 판매자 기능을 사용할 수 있다는 정책을 설명한다.

### 4.3 관리자: 매장 승인

- `매장 승인` 탭을 연다.
- `승인대기 디저트샵`이 `PENDING` 상태인 것을 보여준다.
- 승인 버튼을 눌러 소비자 검색 대상이 될 수 있게 한다.
- 소비자 검색은 `stores.approval_status = 'APPROVED'`인 매장만 노출한다고 설명한다.

### 4.4 판매자: 상품/재고 관리

- `seller_ready`로 로그인한다.
- `두쫀쿠마스터` 또는 `버터떡마스터`를 선택한다.
- 등록 상품과 재고를 확인한다.
- 예약 가능 재고 수량을 변경하고 저장한다.
- 상품 등록 화면에서 새 상품의 대표 이미지, 카테고리, 가격, 총 재고, 예약 가능 재고를 입력할 수 있음을 보여준다.

### 4.5 소비자: 위치/상품 검색

- `consumer1`로 로그인한다.
- 검색창에 `인하대학교 후문 두쫀쿠`를 입력한다.
- Kakao Local API로 `인하대학교 후문` 좌표를 찾고, 해당 기준 위치 주변 DB 매장을 조회한다고 설명한다.
- 지도 마커, 매장 카드, 가게 정보 화면을 확인한다.
- 검색 로그에는 사용자, 기준 키워드, 검색 기준 위치, 결과 수가 저장된다고 설명한다.

### 4.6 소비자: 예약

- `두쫀쿠마스터`에서 예약 화면으로 이동한다.
- 영업시간 안의 방문 예정 시간을 선택한다.
- 수량을 입력하고 예약을 생성한다.
- 예약 가능 재고가 감소하고 예약된 재고가 증가하는 구조를 설명한다.
- 예약 생성은 트랜잭션으로 처리되어 동시 예약 시 재고가 음수가 되지 않는다고 설명한다.

### 4.7 소비자: 내 예약 확인/취소

- `내 예약` 화면으로 이동한다.
- 방금 생성한 예약 내역을 확인한다.
- `가게 정보` 버튼으로 예약한 매장 정보에 접근할 수 있음을 보여준다.
- 필요하면 예약 취소를 시연한다.

### 4.8 판매자: 예약 처리

- `seller_ready`로 다시 로그인한다.
- 예약 목록에서 소비자가 만든 예약을 확인한다.
- 예약 승인, 취소, 수령 완료 처리 흐름을 보여준다.
- 상태 변경 이력은 `reservation_status_logs`에 기록된다고 설명한다.

### 4.9 관리자: 검색 로그/미매핑 관리

- `admin1`로 로그인한다.
- `검색 로그` 탭에서 페이지네이션, 매핑 상태, 사용자, 검색 기준 위치를 확인한다.
- `미매핑 검색어` 탭에서 `말차푸딩` 또는 `크림붕어빵`을 선택한다.
- 기존 키워드 별칭 등록 또는 새 기준 키워드 생성 흐름을 보여준다.
- 처리 완료된 미매핑 검색어는 큐에서 삭제할 수 있고, 등록된 Keyword/KeywordAlias는 유지된다고 설명한다.

## 5. 발표 중 주의사항

- 예약 방문 예정 시간은 매장 영업시간 안으로 선택한다.
- `seller_pending` 계정은 승인 전 판매자 기능이 막히는 것이 정상이다.
- 소비자 검색 결과는 승인된 매장과 활성 상품만 노출된다.
- 상품 이미지 파일이 실제로 없더라도 백엔드가 `/uploads/products/:fileName` fallback 이미지를 제공한다.
- 검색 위치는 사용자의 GPS 위치가 아니라 검색 결과를 계산한 기준 위치이다.

## 6. 발표 후 DB 확인 포인트

- `reservations`: 예약 행 생성 및 상태 변경 확인
- `inventories`: `reservable_stock`, `reserved_stock` 변화 확인
- `reservation_status_logs`: 예약 상태 변경 이력 확인
- `search_logs`: 사용자 검색 기록, 기준 키워드, 검색 기준 위치 확인
- `unmapped_searches`: 미매핑 검색어 처리 상태 확인
- `keyword_aliases`: 별칭 등록 결과 확인
