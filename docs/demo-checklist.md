# 시연 플로우 체크리스트

최종 수정일: 2026-05-22

이 문서는 `database/schema.sql`과 `database/demo-reset.sql`을 적용한 시연용 DB 상태를 기준으로 한다.

## 1. 시연 URL

EC2 배포 접속 URL:

```text
http://13.220.26.183/
```

주의:

- EC2 인스턴스가 실행 중이어야 한다.
- Nginx, Node.js 백엔드, MariaDB가 실행 중이어야 한다.
- Kakao Developers의 JavaScript SDK 도메인에 위 URL이 등록되어 있어야 한다.
- EC2 퍼블릭 IP가 바뀌면 프론트 `.env`, Kakao Developers 도메인, 발표 URL을 모두 다시 확인해야 한다.

```bash

```

Nginx 외부 접속 확인:

## 5. 전체 발표 흐름

### 5.1 시스템 구조 소개

설명 포인트:

- React 프론트엔드
- Node.js/Express 백엔드
- MariaDB 데이터베이스
- Nginx를 통한 정적 파일 제공 및 API 프록시
- Kakao Map JavaScript API
- Kakao Local REST API

강조:

- 프론트는 DB에 직접 접근하지 않는다.
- 모든 데이터 변경은 백엔드 API를 통해 처리한다.
- 예약과 재고 변경은 트랜잭션으로 처리한다.

### 5.2 로그인 및 역할 분리

체크:

- [ ] `admin1`로 로그인하면 관리자 화면으로 이동한다.
- [ ] `consumer1`로 로그인하면 소비자 화면으로 이동한다.
- [ ] `seller_ready`로 로그인하면 판매자 화면으로 이동한다.
- [ ] 로그인 화면에는 역할 선택 버튼이 없고, DB의 `users.role`이 화면을 결정한다.

설명 포인트:

- 공통 사용자 테이블 `users`
- 역할별 프로필 테이블 `consumer_profiles`, `seller_profiles`, `admin_profiles`

### 5.3 관리자 판매자 승인

절차:

1. `admin1`로 로그인한다.
2. `판매자 승인` 탭으로 이동한다.
3. `seller_pending` 또는 승인 대기 판매자 데이터를 확인한다.
4. 승인 버튼을 눌러 상태를 `APPROVED`로 변경한다.

체크:

- [ ] 승인 대기 판매자가 표시된다.
- [ ] 승인 처리 후 상태가 변경된다.
- [ ] 판매자 승인 상태가 DB의 `seller_profiles.approval_status`에 반영된다.

설명 포인트:

- 사용자 계정 활성 상태와 판매자 승인 상태는 별도로 관리한다.
- 승인되지 않은 판매자는 정상적인 판매자 기능 사용이 제한된다.

### 5.4 관리자 매장 승인

절차:

1. 관리자 화면에서 `매장 승인` 탭으로 이동한다.
2. `승인대기 디저트샵`을 확인한다.
3. 승인 버튼을 누른다.

체크:

- [ ] 승인 대기 매장이 표시된다.
- [ ] 승인 처리 후 소비자 검색 대상이 된다.
- [ ] DB의 `stores.approval_status`가 변경된다.

설명 포인트:

- 소비자 검색 결과는 승인된 매장만 표시한다.
- 매장 좌표는 주소 기반으로 저장되어 위치 검색에 사용된다.

### 5.5 판매자 매장/상품/재고 관리

절차:

1. `seller_ready`로 로그인한다.
2. 판매자 메인에서 매장 목록을 확인한다.
3. 등록 상품과 재고를 확인한다.
4. 예약 가능 재고 값을 변경한 뒤 저장한다.
5. 상품 등록 화면으로 이동한다.
6. 상품명, 카테고리, 가격, 대표 이미지, 전체 재고, 예약 가능 재고를 입력한다.

체크:

- [ ] 판매자 본인의 매장만 표시된다.
- [ ] 상품 목록이 매장별로 표시된다.
- [ ] 재고 변경은 저장 버튼을 눌러야 반영된다.
- [ ] 상품 이미지는 업로드 후 화면에 표시된다.
- [ ] DB에는 이미지 파일이 아니라 `products.image_url`만 저장된다.

설명 포인트:

- 판매자 1명은 여러 매장을 가질 수 있다.
- Store와 Product는 Inventory를 통해 연결된다.
- Inventory가 매장별 재고 상태를 담당한다.

### 5.6 소비자 위치/상품 검색

절차:

1. `consumer1`로 로그인한다.
2. 소비자 메인에서 카카오맵이 표시되는지 확인한다.
3. 검색어 `인하대학교 후문 두쫀쿠`를 입력한다.
4. 지도 마커와 검색 결과 매장을 확인한다.
5. 매장 카드를 클릭하면 지도 패널이 유지되는지 확인한다.
6. `가게 정보`로 이동해 매장 상세와 상품 목록을 확인한다.

체크:

- [ ] 검색창은 초기에는 비어 있다.
- [ ] 카카오맵이 표시된다.
- [ ] 장소+상품 검색이 동작한다.
- [ ] 검색 기준 위치가 `인하대학교 후문`으로 표시된다.
- [ ] 해당 위치 주변의 승인 매장만 표시된다.
- [ ] 매장 카드와 지도 마커가 연동된다.
- [ ] 매장 정보 화면으로 이동할 수 있다.

설명 포인트:

- 검색어에서 상품 후보와 장소 후보를 분리한다.
- 장소 후보는 Kakao Local REST API로 좌표 변환한다.
- 변환된 좌표 주변의 DB 매장을 조회한다.
- 검색 로그에는 원본 검색어, 기준 키워드, 검색 기준 위치, 결과 수가 저장된다.

### 5.7 소비자 예약

절차:

1. 검색 결과에서 `이 매장에서 예약하기`를 누른다.
2. 예약 수량을 선택한다.
3. 방문 예정 시간을 매장 영업시간 안으로 선택한다.
4. 예약을 생성한다.
5. 예약 완료 메시지를 확인한다.
6. `내 예약 보기`로 이동한다.

체크:

- [ ] 예약 가능 재고보다 많은 수량은 선택할 수 없다.
- [ ] 방문 예정 시간이 현재보다 30분 이후인지 검증된다.
- [ ] 영업시간 밖 예약은 차단된다.
- [ ] 예약 생성 후 예약 가능 재고가 감소한다.
- [ ] 내 예약 목록에 방금 만든 예약이 표시된다.
- [ ] 예약한 매장의 `가게 정보`로 이동할 수 있다.

설명 포인트:

- 예약 생성은 재고 차감과 예약 생성을 하나의 트랜잭션으로 처리한다.
- 동시 예약 시 `SELECT ... FOR UPDATE`와 조건부 UPDATE로 재고 음수를 방지한다.

### 5.8 판매자 예약 처리

절차:

1. `seller_ready`로 다시 로그인한다.
2. 예약 목록에서 소비자가 만든 예약을 확인한다.
3. 예약 승인 버튼을 누른다.
4. 필요하면 수령 완료 또는 예약 취소를 처리한다.

체크:

- [ ] 소비자 예약이 판매자 예약 목록에 표시된다.
- [ ] 예약 승인 상태가 반영된다.
- [ ] 수령 완료 시 `reserved_stock`이 감소한다.
- [ ] 예약 취소 시 `reserved_stock`이 감소하고 `reservable_stock`이 복구된다.
- [ ] 상태 변경 이력이 `reservation_status_logs`에 기록된다.

설명 포인트:

- 예약 상태 전이는 제한된 방향으로만 허용된다.
- 상태 변경과 재고 변경은 같은 트랜잭션으로 처리한다.

### 5.9 관리자 검색 로그 확인

절차:

1. `admin1`로 로그인한다.
2. `검색 로그` 탭으로 이동한다.
3. 방금 소비자가 검색한 로그를 확인한다.
4. 페이지네이션을 확인한다.

체크:

- [ ] 검색어 원문이 표시된다.
- [ ] 기준 키워드가 표시된다.
- [ ] 사용자 정보가 표시된다.
- [ ] 검색 기준 위치가 표시된다.
- [ ] 결과 수가 표시된다.
- [ ] 페이지당 로그 수를 변경할 수 있다.

설명 포인트:

- 검색 로그는 인기 검색어 산정 근거이다.
- 검색 기준 위치는 사용자의 GPS가 아니라 해당 검색이 기준으로 삼은 장소이다.

### 5.10 관리자 미매핑 검색어 처리

절차:

1. 관리자 화면에서 `미매핑 검색어` 탭으로 이동한다.
2. 검토 대기 검색어를 선택한다.
3. 기존 기준 키워드에 별칭으로 등록한다.
4. 또는 새 기준 키워드를 생성한다.
5. 보류, 반려, 삭제 기능도 확인한다.

체크:

- [ ] 미매핑 검색어 목록이 표시된다.
- [ ] 기존 키워드의 별칭으로 등록할 수 있다.
- [ ] 새 키워드를 생성할 수 있다.
- [ ] 기준 키워드 제약 조건이 적용된다.
- [ ] 보류와 반려 상태를 구분할 수 있다.
- [ ] 삭제가 가능하다.
- [ ] 처리 후 Keyword/KeywordAlias 데이터가 유지된다.

설명 포인트:

- 매핑 실패 검색어는 바로 버리지 않고 운영자가 관리한다.
- 별칭이 등록되면 이후 같은 검색어는 기준 키워드로 매핑된다.

### 5.11 최근 인기 검색어 확인

절차:

1. 소비자 화면으로 이동한다.
2. 최근 7일 인기 검색어 영역을 확인한다.
3. 검색을 여러 번 수행한 뒤 인기 검색어의 횟수가 반영되는지 확인한다.

체크:

- [ ] 인기 검색어는 Product가 아니라 Keyword 기준으로 표시된다.
- [ ] 최근 7일 검색 로그 기준으로 검색 수가 집계된다.
- [ ] 검색 로그가 부족하면 관리자 trend_score 기반 추천이 표시될 수 있다.

설명 포인트:

- 같은 키워드의 상품이라도 매장별 가격과 이미지가 다를 수 있으므로 랭킹은 Keyword 기준이다.

## 6. 발표 중 DB 확인 포인트

HeidiSQL 또는 MariaDB CLI에서 확인할 테이블:

- `users`: 역할별 계정
- `seller_profiles`: 판매자 승인 상태
- `stores`: 매장 승인 상태와 좌표
- `products`: 상품 정보와 이미지 URL
- `inventories`: 재고 변화
- `reservations`: 예약 생성과 상태
- `reservation_status_logs`: 예약 상태 변경 이력
- `search_logs`: 검색 기록
- `unmapped_searches`: 미매핑 검색어 상태
- `keyword_aliases`: 별칭 등록 결과
- `location_cache`: 장소 좌표 캐시

추천 확인 SQL:

```sql
SELECT reservation_id, user_id, inventory_id, quantity, status, visit_time, created_at
FROM reservations
ORDER BY reservation_id DESC;

SELECT inventory_id, store_id, product_id, total_stock, reservable_stock, reserved_stock
FROM inventories
ORDER BY inventory_id;

SELECT raw_query, keyword_id, location_query, result_count, mapping_status, created_at
FROM search_logs
ORDER BY log_id DESC;

SELECT raw_query, count, status, resolved_action, resolution_note
FROM unmapped_searches
ORDER BY unmapped_id DESC;
```

## 7. 발표 중 주의사항

- 예약 방문 예정 시간은 반드시 매장 영업시간 안으로 선택한다.
- EC2 IP가 바뀌면 카카오 JavaScript SDK 도메인도 다시 등록해야 한다.
- 발표 전 `database/demo-reset.sql`을 실행하면 시연 데이터가 초기화된다.
- 초기화 후에는 기존 예약, 검색 로그, 미매핑 처리 결과가 리셋된다.
- 이미지가 보이지 않으면 `/uploads` 프록시와 백엔드 업로드 경로를 먼저 확인한다.
- 지도 오류가 나면 브라우저 개발자도구 Network에서 Kakao SDK 요청 상태를 확인한다.

## 8. 발표 마무리 요약 멘트

본 시스템은 단순 상품 검색 서비스가 아니라, 사용자 역할별 데이터 관리, 위치 기반 매장 조회, 매장별 재고 분리, 예약 트랜잭션, 검색 로그 기반 키워드 관리까지 연결한 데이터베이스 중심 시스템이다. 특히 예약 기능에서는 재고 차감과 예약 생성이 하나의 트랜잭션으로 처리되며, 검색 기능에서는 사용자의 자연어 검색을 Keyword/KeywordAlias 구조로 정규화해 유행 상품 데이터를 관리한다.
